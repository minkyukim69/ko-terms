# chat 프로젝트 용어 — chat 이 만든 말과 정한 뜻

> Skill `ko-terms` 의 참조 파일이다. **chat 레포지토리**(`github.com/minkyukim69/chat` · SAP 분석 · 설계 · 개발 채팅)의 말이다. 트로브의 말은 `trove-terms.md` 에 있다.
> 출처: chat CLAUDE.md 0-5-2 «풀어 쓰는 말」 의 chat 행 · chat 설계서들의 «이 문서에 나오는 용어」 표(2026-11-27 모음). Version 뜻의 «판」 은 «버전」 으로 고쳐 옮겼다(결정 K4).
> 결정의 정본은 chat CLAUDE.md · `docs/` 설계서다 — 이 파일은 «말의 뜻」 만 적고, 규칙 번호(CR · GR · U) · 설계서 절로 그 정본을 가리킨다. 뜻이 바뀌면 설계서를 고치는 커밋에서 이 파일도 고친다.
> 코드 식별자(예: `pin_run` · `reference_doc`)는 그대로 두고 설명만 이 말로 쓴다.
> 🔴 **버전 표기**: chat 문서도 Version 을 오래 «판」 이라고 썼다(판 고정 · 활성 판 · 이름@판 · 설계서 v 판 — `CLAUDE.md` + `docs/*.md` 약 1,340곳 · 2026-11-27 hook 규칙 T01 모양으로 셈 · 다른 뜻이 섞였을 수 있다). 화면 문구는 이미 «버전」 이다(2026-11-02). 이 Skill 의 결정(K4)대로 **새 글은 «버전」** 으로 쓴다. 아래 표는 «버전」 으로 적고 문서에 굳은 옛 표기를 괄호로 단다 — 문서를 검색할 때는 옛 표기로 찾는다. 남은 옛 표기는 chat 문서 정리 때 한 자리씩 읽어 고친다(일괄 치환 금지).
> 문서에 굳은 말 중 현장 말과 다른 것(머리글 · 머리말 · 쪽 · 묶음 …)은 `it-terms.md` G절(결정 대기)에 모았다. 2026-11-27 결정으로 표지 → 구분자 · 되돌림 → 재작성 요청 · 봉함 → 암호화 저장 · 봉투 → 공통 구조 · 자리표시 → skeleton 노드 · 플레이스홀더 · 이름표 → 라벨 · 이어받기 → 연속 조회 · 잰다 → 측정한다로 바꿨다(chat 문서 · 코드 · 자산을 같은 날 고침 — 기록 문서 · 변경 이력에는 옛 표기가 남는다).

## A. 시스템 · 경계

| 용어 | 풀이 |
|---|---|
| chat | SAP 컨설턴트 · 개발자가 **대화로** SAP 시스템을 분석 · 설계 · 개발하게 돕는 시스템. 레포지토리 = 로컬 `/home/agent/projects/chat` + 원격 `github.com/minkyukim69/chat` |
| 트로브(Trove) | SAP 용 **MCP 서버**. chat 이 **고객사 SAP 시스템**에 관한 사실을 얻는 유일한 곳이다(CR1). 레포지토리 = `github.com/minkyukim69/trove` |
| 고객사 SAP 시스템(chat 에서) | 트로브가 관리하는 고객사의 SAP 접속(접속 이름) 하나하나와 그 시스템에만 있는 사실. 정본은 트로브 하나다(CR1). 일반 SAP 지식은 다른 MCP 서버로도 얻을 수 있다(CR12 · U82). 뜻 자체는 `sap-terms.md` |
| 접속 이름(chat 에서) | chat 은 SAP 시스템을 **접속 이름으로** 가리킨다 — SID · client 는 고객사끼리 겹칠 수 있어 열쇠로 쓰지 않고 접속의 속성으로만 본다(설계서 §7-6 · U62). 뜻 자체는 `sap-terms.md` |
| MCP 서버(등록) | chat 에 **admin 이 등록한 MCP 서버** — 트로브 + 일반 SAP 지식 서버 + 업무 도구 서버(이슈 · 문서 · 코드 레포지토리 등). 호출은 모두 MCP 관문 한 곳을 지난다(CR2 · CR12) |
| MCP 관문 | 모든 MCP 서버 · 트로브 연계 API 호출이 지나는 **단일 관문**(`chat/core/mcp_gate.py`) — 인증 주입 · 오류 변환 · 상한을 한 곳에서 한다(CR2) |
| MCP API · 연계 API | 트로브의 두 외부 진입점(트로브 확정 이름) — **MCP API**(`/mcp` — LLM 이 대화 중에 tool 을 고른다) · **연계 API**(`/v1` — chat 의 프로그램 코드가 정해진 순서로 부른다). 연계 API 의 정본은 트로브의 `/v1/openapi.json` · 요청 목록은 chat `docs/trove_api_requests.md` |
| Site · Site Key | **트로브의** 개념 — 트로브를 쓰는 고객사 · 외부 시스템 단위 · 그 Site 에 발급된 API 키(`trv_` 로 시작). chat 은 트로브에게 **하나의 Site** 이고, 트로브가 발급한 Site Key **하나**를 서버 비밀값으로 갖는다. chat 자신은 Site · 키를 발급하거나 관리하지 않는다(chat CLAUDE.md §1-1) |
| 트로브 대역(시험용) | 트로브에 아직 tool 이 없는 동안 고객사 SAP 시스템 용도를 시험용으로 붙인 다른 MCP 서버의 표시(U159 — 운영에서는 끈다). 시험 코드의 «대역(fake)」 과 같은 뜻의 말이다 |
| 정보 원천 | 메인 LLM 이 질문 유형마다 고르는 출처(고객사 시스템 · SAP 표준 · 사내 문서 · 업무 자료 · 일반 웹 …). 서버마다 용도 · 상태 · 짧은 설명을 «정보 원천 줄」 로 받는다(orchestration_design §21) |
| outbound · egress | **outbound** = 밖과 통하는 도구(내장 web · stdio MCP)만 도는 컨테이너 · **egress** = 허용 도메인만 통과시키는 유일한 나가는 문(CR13) |
| 실행 샌드박스 | LLM · 사용자가 쓴 Python 코드를 돌리는 격리 컨테이너(`sandbox` — CR11). 비밀값이 없고 밖으로 나가지 못한다 |

## B. 사용자 · 자산

| 용어 | 풀이 |
|---|---|
| 일반 사용자 · admin | chat 의 **사용자 역할 둘**. admin = 사용자 관리 · 설정까지 · 일반 사용자 = 대화 · 산출물(chat CLAUDE.md §1-1) |
| UQID | 사용자마다 하나인 다섯 자리 글자(36진법 `00000` ~ `ZZZZZ` · 초기 관리자 `00000`) — 바꾸지 않는다(U231 · U252) |
| 사용자별 SAP 접속 정보 | chat 사용자가 **자기 SAP 계정**(ID · 비밀번호 · 로그온 언어)을 **SAP 접속마다** 등록한 것. **개발의 SAP 쓰기에만** 쓴다(CR8) |
| 시스템 그룹 | chat 이 **접속 이름 몇 개를 묶은 단위**(예 한 고객사의 DEV · QAS · PRD). 설계개발표준 하나를 그룹 하나에 붙인다(U63) |
| System Prompt · Skill | LLM 에 싣는 **자산** — 이름 · 버전 · 활성으로 관리한다(GR10 · GR30). System Variant(System Prompt + 생성 파라미터 묶음)는 **쓰지 않는다**(U72) · 저장 자산 «User Prompt」 도 **두지 않는다**(U81 — 사용자가 대화창에 치는 글은 자산이 아니다) |
| General Skill · 고객 Skill | **General Skill** = 관리 › Skill (General) 에서 관리하는 chat 전체 공통 Skill · **고객 Skill** = 메뉴 «고객 표준」 이 만든 그 고객사(또는 시스템 그룹)만의 기준(코드 이름 `reference_doc` — U237) |
| 고객 표준 · 표준안 · 양식 | **고객 표준** = 고객 Skill 의 화면 이름 · **표준안** = 그 고객 Skill 로 저장한 md 문서의 화면 이름 · **양식** = 문서 하나를 어떻게 만드는지 담은 작성 Skill(머리말 `kind: doc_author`)(standard_docs_design) |
| 작성 용도 | 그 고객 Skill 을 고를 수 있는 대화 용도(예전 «assign · 쓸 곳」 — U259 · 코드 이름 `targets`) |
| 플레이북 | 여러 MCP tool 을 **정해진 순서로 엮어 쓰는 절차**를 적은 Skill(머리말 `kind: playbook`). 대화창에서 서버처럼 켜고 끈다(U117) · 플레이북 에이전트 = 그것을 만드는 admin 전용 대화 용도(U173) |
| 산출물 | 대화로 만든 **분석서 · 설계서 · 코드** 같은 결과 문서 |

## C. 대화 엔진 · 오케스트레이션

| 용어 | 풀이 |
|---|---|
| 턴(turn) | 사용자 입력 하나에서 시작해 **chat 이 최종 답을 낼 때까지**의 한 차례. 그 사이 LLM ↔ tool 호출이 여러 번 오갈 수 있다 |
| run | 사용자 글 하나에서 시작해 답이 나올 때까지의 **작업 하나**. PG 에 로우로 있고 worker 가 돌린다. 대화 하나에는 동시에 run 하나만(U98 ⑤) |
| tool 호출 루프 | LLM 이 tool 호출을 요청하면 chat 이 실행해 결과를 돌려주고, LLM 이 다시 판단하는 **반복** |
| 용도(purpose) | 기능 화면(채팅 · 설계 · 개발 · 역설계 · 고객 표준 …). 오케스트레이션 구성은 공유하고, 용도마다 자산 · 주입 정보 · 출력 형식이 다르다(U99 ①) |
| 역할(role) | 한 run 안에서 LLM 을 부르는 **자리** — 메인 · 입력 판정 · 하위 조사 · 검토 · 정리 · 마무리 · writer …. 이름은 코드가 선언한다 |
| 결속 | (용도, 역할) → 모델 설정 · System Prompt · Skill · 출력 예산 · 검토 횟수를 정한 표(binding — orchestration_design §5) |
| 버전 고정(문서 표기 «판 고정」) · 스냅샷 | run 이 시작될 때 모든 역할의 System Prompt · Skill 버전 · 합친 params 를 run 에 적어 두고 끝까지 그것만 쓰는 것(코드 `pin_run` — U97 ③) |
| 확장 지점 | 기능이 공유 오케스트레이션에 자기 것을 꽂는 자리 — 주입 정보 공급자 · 출력 형식 · 역할 구성 · 기능 tool(`feature_tool`)(orchestration_design §3-1) |
| 안전지점 | 진행 중인 run 에 새 입력을 넣거나 멈출 수 있는 자리 — LLM 응답이 끝난 뒤 · tool 묶음이 끝난 뒤 등(U98) |
| 대기 입력 | run 이 도는 중에 들어온 사용자 글. 받는 즉시 PG 에 두고 안전지점에서 주입한다(U96 ④) |
| 끼어들기 · 방향 수정 | «방향 수정」 입력이 오면 진행 중인 LLM 생성 · 읽기 tool 을 끊고 새 글을 넣어 다시 부르는 것(U96 ⑥) |
| 체크포인트 | run 을 다시 시작할 때 이어 갈 자리 — 마지막으로 처리가 끝난 단계까지의 메시지 · tool 결과 · 사용량 |
| 하위 조사 | 메인이 맡기는 독립된 작은 조사. 자식 run 으로 동시에 돈다(U203 · orchestration_design §10) · 사람에게 묻지 않는다 |
| HITL · 멈춤 | run 이 사람의 결정을 기다리며 서는 것 — 승인 카드 · 질문 카드 · 상한 카드 · 계속 불가(orchestration_design §11) |
| 승인 카드 | 쓰기로 보는 tool 을 실행하기 전에 사람의 승인을 받는 화면 카드(CR12). 승인 방식 `manual` · `auto` 는 사용자가 대화창에서 고른다(U110) |
| 질문 카드 | LLM 이 사람에게 결정을 묻는 화면 카드(질문 1 ~ 4 · 선택지 · 기타 — U255) |
| 조견표 | 답 · 장의 주장마다 «근거가 어느 tool 호출인가」 를 적은 표. 코드가 이번 호출과 대조해 점검한다(`answer_check` — U128 · U131) |
| 데이터 줄 · 구분자(문서 표기 «표지」) | 엔진이 LLM 에 주는 **데이터**(지시가 아님)를 알리는 한 줄 · 그 경계를 알리는 글자 표시(예: `[역설계 대상 — 데이터]`). 규칙 문장은 자산에, 구조는 코드에 둔다(orchestration_design §19) |
| 계획(plan) | 대화창 요청의 «적용될 설정」(LLM · 도구 옵션 · 승인 방식 · SAP 접속 · 고객 표준). 글을 올릴 때 run 에 고정된다(`chat_plan`) |

## D. 문서 검색(QD)

| 용어 | 풀이 |
|---|---|
| 벡터 DB(chat 에서) | chat 의 벡터 DB(Qdrant)의 내용은 **색인**이고 원본(문서 메타 · 버전 · 청크 글 · 권한)은 PG 다 — 사라져도 PG 에서 다시 만든다(CR9). 뜻 자체는 `it-terms.md` E절 |
| QD · QD 등록 | 문서 검색 기능 — **Q**drant 에 색인한 **D**ocument · 사람이 문서를 최종 산출물로 확정해 검색 대상으로 올리는 동작(CR9 · qd_design) |
| 문서 묶음 | 문서를 담는 폴더 같은 단위. 용도 · 볼 수 있는 범위 · LLM 에 주는 설명을 묶음에 건다(U158) |
| 색인 작업 | 문서 버전 하나를 청크로 나누고 임베딩해 Qdrant 에 넣는(또는 지우는) worker 의 일 하나(`index_job` — U168) |
| 청크 설정 | 문서 종류마다 청크를 어떻게 나눌지 정한 값 묶음(토큰 예산 등 — U180) |
| 정합 점검 | 문서마다 «PG 청크 수 = Qdrant 점 수」 를 대조하는 일(CR9) |
| 별칭(alias) | Qdrant 컬렉션을 가리키는 이름. 코드는 별칭 `chat_docs` 만 쓰고, 모델을 바꿀 때 새 컬렉션을 다 만든 뒤 별칭을 한 번에 돌린다(GR16) |

## E. 역설계

| 용어 | 풀이 |
|---|---|
| 역설계서 | 현행 SAP 객체(프로그램 · 서비스)가 **지금 어떻게 동작하는지** 사실로 적은 문서. 옮길 곳의 대응 · 구현 방법은 담지 않는다(U263) |
| 요약본 · 이관용 상세(C2C · C2R · R2R) | 업무 담당자도 읽는 짧은 역설계서 · 다시 만들 수 있을 만큼 자세한 역설계서(Classic → Classic · Classic → RAP · RAP · SEGW → RAP)(reverse_doc_design §0) |
| 양식 Skill(역설계) | 역설계서의 장 구성과 쓰는 법을 담은 Skill(머리말 `kind: reverse_form`). 코드는 장 **키**만 안다 |
| 사실 장 · 뜻 장 | **사실 장** = 정답이 하나인 장 — 코드가 재료와 트로브 조회로 만든다(출처 `code` · 잠금) / **뜻 장** = 해석이 필요한 장 — LLM 이 장마다 한 번 쓴다(출처 `llm` · 사람이 고치면 `human`)(reverse_doc_design §15) |
| 재료 · 읽기 묶음 | **읽기 묶음** = 트로브가 객체 하나의 소스를 읽는 순서대로 묶어 주는 응답(연계 API `/v1/reverse-pack`) · **재료** = chat 이 그것을 끝까지 받아 잠시 보관한 것(10일 — U286) |
| 생성기 · writer | 사실 장을 만드는 코드(`reverse_generate`) · 뜻 장을 쓰는 LLM 역할(결속 `(reverse, writer)`) |
| 담당자 · 전달 | 주인이 역설계서마다 지정한 사람과 그 동작. 담당자는 보완 · 저장 · QD 등록을 위임받는다(U266) |
| 등록본 | QD 에 올라간 역설계서 버전. 새 버전을 저장해도 그대로이고 [다시 등록] 으로만 바뀐다(U276) |
| 다시 생성 · stale | [다시 생성] = 재료를 다시 받고 사실 장을 코드가 다시 만드는 버튼 · stale = 그 뒤 아직 다시 쓰지 않은 뜻 장의 표시 |

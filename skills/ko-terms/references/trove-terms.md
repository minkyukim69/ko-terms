> Skill `ko-terms` 의 참조 파일이다. **트로브 레포지토리**(`github.com/minkyukim69/trove` · SAP 사실을 내주는 MCP 서버)의 말이다. chat 의 말은 `chat-terms.md` 에 있다.
> 출처: 트로브 CLAUDE.md 0-5-2 · §0-6 · §1-0 · §1-1(2026-11-27 chat 쪽에서 처음 옮김) + **2026-11-27 트로브 쪽 보강** — 설계서마다 머리에 있는 «이 문서에 나오는 용어」 표(30여 곳) · 적재 표준 IG1 ~ IG19(`docs/ingest_design.md`) · API 설계 MA1 ~ MA43 과 §5-4(`docs/mcp_api_design.md`)의 말을 더했다(트로브 커밋 `04d52ea9` 기준).
> 결정의 정본은 트로브 CLAUDE.md · `docs/` 설계서다 — 이 파일은 «말의 뜻」 만 적고 괄호 안에 정본 자리를 적는다. 문서 이름의 짧은 꼴: 적재 개괄 = `docs/ingest_design.md` · 적재 상세 = `docs/ingest_detail_design.md` · API 설계 = `docs/mcp_api_design.md` · 배치 설계 = `docs/batch_design.md` · 고객화 설계 = `docs/config_analysis.md` · 해석서 만들기 = `docs/config_doc_design.md` · 대화 설계 = `docs/chat_design.md` · Help 가져오기 = `docs/help_scrapping.md` · 읽기 묶음 = `docs/reverse_reading_design.md` · 백업 = `docs/backup_restore.md` · 형식 변경 = `docs/ingest_change.md` · ADT 설계 = `docs/adt_design.md`.

## A. 시스템 · 경계

| 용어 | 풀이 |
|---|---|
| 트로브(Trove) | SAP Upgrade · Conversion 을 돕는 **MCP 서버** — 역설계 · 설계 · 개발에 필요한 **SAP 사실**을 MCP API · 연계 API 로 내준다. 산출물은 담지 않는다(chat 이 저장). 영어 *treasure trove*(귀한 것을 모아 둔 곳)에서 왔고 «트로브」 로 읽는다(CLAUDE.md §1-0) |
| MCP API · 연계 API | 트로브의 두 외부 진입점 — **MCP API**(`/mcp` — LLM 이 대화 중에 tool 을 고른다) · **연계 API**(`/v1` — 소비자의 프로그램 코드가 정해진 순서로 부른다 · 정본 `/v1/openapi.json` · 하위 호환을 지킨다, 바꾸려면 `/v2`). tool 이름 · 응답에 프로젝트 이름을 붙이지 않는다(§1-0 · §1-2) |
| `/admin` | 콘솔 전용 API. 콘솔 BFF 만 부른다(내부망) — 외부 계약이 아니다(§1-2) |
| 해석 전용 주소(`/mcp/config`) | 고객화 해석서를 만드는 쪽만 쓰는 MCP 주소. 이 주소에만 있는 tool(`compare_standard_template` · `get_config_pack`)이 있고, 허용 tool · 금지 인자 값 · 금지 문서 원천을 따로 정한다(해석서 만들기 §23-3 · §23-4) |
| Site · Site Key | 트로브를 쓰는 고객사 · 외부 시스템 단위 · 그 Site 에 발급한 API 키(`trv_<공개 12자>_<비밀 43자>` · 발급 화면에서 한 번만 보인다 · ID 없이 키 하나로 `/mcp` · `/v1`). 헤더를 못 넣는 MCP 클라이언트는 OAuth(토큰은 Site Key 에 묶임)를 쓴다(§1-1 · architecture §7) |
| 콘솔 · 콘솔 사용자 | 트로브의 **두 번째 소비자** — 관리(사용자 · Site · Key · 모델 자원 · SAP 접속 · 배치 · 로그 · tool 점검) + 콘솔 대화 · 그 화면에 아이디 · 비밀번호로 로그인하는 사람(§1-1) |
| 주체(principal) | 요청을 보낸 «누구」 — **Site** 와 **콘솔 사용자** 두 종류. 판정 함수는 `resolve_principal` 하나(architecture §6-1). 고객화 해석서의 «주체」(무엇에 대한 해석서인가 — H절)와 다른 말이다 |
| scope | 연계 API 의 권한 단위 이름(`이름:동작` — 예 `connections:read`). 기본 열림이고 관리자가 Site 마다 뺄 수 있다(architecture §8-4) |
| SAP 접속 · 접속 이름(`connection`) | SAP 시스템 하나로 가는 접속과 그 이름(예 `ACME-DEV-100`). 트로브 안에서 유일하고 바꿀 수 없으며, tool 이 SAP 시스템을 가리키는 유일한 인자다 — SID · client 는 고객사 사이에서 유일하지 않다(API 설계 §0-1 · 적재 U5) |
| 시스템 묶음 · 묶음 DEV | `system_landscape` 값이 같은 DEV · QAS · PROD 접속들(현장 말로 «랜드스케이프」) · 그중 용도가 DEV 인 접속. 구조 질문은 묶음 DEV 로 답한다(API 설계 §5-4-3 · MA20) |
| `graph_connection` | 구조 · ADT 를 실제로 읽은 접속. 받은 접속과 다를 때만(QAS · PROD 를 물어 묶음 DEV 로 답했을 때) 응답에 싣는다(API 설계 §5-4-6) |
| 보호 용도 | 승인 · 접속 선택을 따져야 하는 접속 용도(DEV 가 아닌 것 · 모르는 용도 포함 — `site_access.is_guarded`) |
| SAP 메타 정보 | 트로브가 저장하는 고객사 관련 정보의 전부 — 미러 스냅샷 · 그래프 · 객체 설명 · 텍스트 오버라이드. 예외로 고객화 해석서를 저장한다(§1-1) |
| 고객화 해석서 | SAP 접속에 딸린 고객화(설정) 해석 문서(요약본 · 상세분석본). «SAP 메타 정보의 확장」 으로 보고 트로브가 저장한다(§1-1 · 고객화 설계) |
| 모델 자원 · 내장 / 외부 | 트로브가 부르는 chat LLM · 임베딩 · reranker 서버. 콘솔에서 등록하고 종류마다 하나를 활성으로 고른다 · **내장** = compose 안 CPU 전용 컨테이너 `models` · **외부** = 사내 GPU 서버 등 그 밖의 서버(architecture §4 · GR8) |
| 텍스트 오버라이드 | 사람이 고친 이름 · 설명. SAP 접속 단위로 `(유형, 이름, 필드)` 에 걸고, 읽을 때 원문보다 먼저 쓴다 — 그래프에 복사하지 않고 읽을 때 조인한다(GR17) |
| 표준 함수 · 표준 읽기 함수 | 같은 질문에 답하는 함수 하나(GR28 · 목록 = CLAUDE.md §11). tool · 연계 API · 콘솔이 같은 함수를 부른다 — 같은 질문에 답하는 함수를 새로 만들지 않는다 |
| 등록부 | 코드가 기대는 정의(SAP 주소 · 하위유형 · 관계 종류 · 상한 · 응답 낱말 · tool 명세 …)를 레포지토리 TSV 원본 → R 파일 → PG 테이블로 관리하는 묶음. 코드에 상수로 적지 않는다(GR28-B · 정의 등록부 설계) |
| 정의 등록부 · 주제(topic) · 키 · PG 사본 | `trove/db/registry/` 의 등록부 한 곳 · 그 한 단위(«질문 한 종류 = 파일 하나」 — 접두 `sap.` · `abap.` · `mcp.` · `limit`) · 주제 안의 한 묶음 · 파일 원본을 PG 로 옮긴 사본(프로세스는 파일을, SQL · 콘솔은 PG 를 읽는다)(`docs/catalog_design.md`) |
| V · S · R 파일 | 마이그레이션 파일 세 종류 — V = 스키마(한 번만 · 커밋 뒤 고치지 않는다) · S = 초기 데이터(한 번만) · R = 자산 · 등록부(내용이 바뀌면 다시 · 생성기가 만든다)(GR29) |
| 가드 | 커밋 때 규칙 위반을 막는 검사 스크립트(`scripts/guard/` — pre-commit). 오탐이면 가드를 끄지 않고 규칙을 고친다(GR35) |
| 보호 데이터 | 시험 · 정리가 절대 건드리지 않는 사용자 데이터(사용자가 넣은 SAP 접속 · Site 등) |

## B. 적재 · 그래프

| 용어 | 풀이 |
|---|---|
| 적재 | SAP 에서 객체 · 관계를 읽어 트로브의 그래프 · 검색 색인에 넣는 일(적재 개괄 · 적재 상세). SAP 에서 테이블을 복제해 오는 «받기」(C절)와 섞지 않는다 |
| 그래프 · 노드 · 엣지 | 적재 결과를 PG 테이블에 담은 것 · 노드 테이블의 로우 하나(SAP 객체 하나 또는 그 하위 요소 하나) · 엣지 테이블의 로우 하나(노드 둘의 연결 하나)(적재 개괄 §0-1) |
| 식별키 | 노드 하나를 가리키는 키 — `(conn_id, object_type, node_kind, name)` + 바뀌지 않는 정수 `id`. 하위유형(`subtype`)은 키가 아니다(IG7) |
| `node_kind` — `object` · `sub` · `ref` | 노드 종류 — SAP 에 자기 이름으로 있는 독립 객체 · 부모가 자기 적재기로 만드는 하위 노드(고정값 · 화면 · FUGR 프로그램 · BAdI 정의 · 타입 그룹 멤버) · **참조 연결점**(부모에 속하지만 가리키는 쪽 적재기가 만든다 — 메서드 · GUI 상태 · 화면 출구). 필드는 노드가 아니다(적재 상세 §0-2) |
| skeleton / full | 이름만 있는 **skeleton 노드**(문서 표기 «자리표시 노드」) / 내용까지 **채워진 노드**. skeleton 은 «없는 객체」 가 아니고 full 을 강등하지 않는다(IG14) |
| 기준안 · 예외 등록부(IX) | 모든 객체 유형이 타는 적재 규칙 하나 · 기준안을 벗어나는 것을 적는 단 한 곳(예외는 IX 번호로 코드 docstring 에도 함께 적는다)(IG1 ~ IG3) |
| 관계 방향 | 엣지는 늘 «쓰는 쪽(dependent) → 쓰이는 쪽(dependency)」. 사용처(영향도)는 들어오는 엣지를 거슬러 찾는다(IG8) |
| 관계 종류(`rel_type`) | 엣지의 종류 이름(`USES` · `CHECKS_AGAINST` · `HAS_FIXED_VALUE` …). 등록부 테이블 + FK 로 DB 가 허용 목록을 지킨다(GR13) |
| 적재기 · 계획(plan) | 유형마다 «이 객체를 이렇게 싣는다」 를 만드는 코드 · 그 결과물(primary · 하위 노드 · 끝점 · 엣지). 적재기는 계획만 만들고 SQL 로 그래프를 쓰지 않는다(적재 상세 §4-1) |
| primary | 적재 한 건의 대상 객체 |
| 단일 관문(`ingest_object`) | 구조 노드 쓰기가 반드시 지나가는 한 곳. merge · 중복 방지 · 패키지 기록을 여기서 한다 — «쓰는 프로세스가 하나」 가 아니라 «쓰기가 지나는 관문이 하나」(IG9) |
| 끝점 | **엣지가 가리키는 남의 노드**. 아직 없으면 skeleton 으로 만든다(적재 상세 §0-2). 그래프 DB 뜻의 «끝점」(끝 노드)이고 API 엔드포인트가 아니다 — 두 뜻의 구분 = `it-terms.md` A1 |
| 주인(`owner_id`) | 엣지를 지우고 바꾸는 적재 단위 = 출발 노드의 객체(출발이 하위 노드면 그 부모)(O1) |
| C · U · D | 처음 적재 · SAP 에서 내용이 바뀐 객체의 재적재 · SAP 에서 사라진 객체의 삭제 |
| 가공 해시 = 적재 해시 · 계획 해시 | 적재기가 만든 계획 전체의 해시(`plan_hash` = 노드 `source_hash`). 같으면 관문이 쓰지 않는다(IG10 · A2) |
| 원천 해시 · 로우 해시 · 객체 원천 해시(`src_obj_hash`) | 가공 전 SAP 결과의 해시 · 미러 로우 하나의 해시 · 한 객체를 이루는 미러 로우 묶음(적재 조합)의 해시 — DELTA 가 다시 계획할 객체를 고른다(적재 상세 §2-8) |
| 부가 해시 | 계획 해시에 넣지 않는 계획 내용(설명 · ref 계획 · 끝점 props · 별칭)의 해시(형식 변경 FX7) |
| 차집합 삭제 · 연쇄 삭제 | «새 목록에 없는 것」 을 지우는 단계(upsert 는 지우지 않는다) · FK `ON DELETE CASCADE` 로 DB 가 함께 지우는 것 |
| 전체 점검 | 적재 회차 끝에 남은 것을 한꺼번에 정리하는 단계 — 사라진 노드 처리 · `ref` 실재 확인 · 아무도 안 가리키는 skeleton · 필드 목록 정리(적재 상세 §4-6) |
| `gone_at` · `loaded_at` | SAP 에서 사라졌는데 남이 아직 가리켜 그 회차에 지우지 않은 노드에 찍는 시각 · 자기 적재기가 primary 에 찍는 적재 표식(«이미 적재됐나」 는 `detail='full'` 이 아니라 이것으로 판정 — IG14) |
| 1단계 · 2단계 적재기 | 자기 노드를 만드는 적재기 전부 · 남의 하위 노드를 가리키는 연결형 적재기(ENHS → ENHO · SXSD · SXCI → TRAN · SMOD) |
| cascade(연쇄 적재) | 한 객체를 적재하면 그것이 가리키는 객체들도 **꼬리를 물고 적재**하는 것. 중지 조건은 «이미 적재(seen-set)」 하나뿐이고 깊이 제한이 없다(IG13). 조직 캐스케이드(H절)와 다른 말이다 |
| seen-set | 이번 연쇄에서 이미 적재한 객체 모음 — 연쇄가 끝나는 것을 보장한다(IG13) |
| 레인(lane) | 작업을 나눠 **동시에** 도는 줄. 미러 받기의 레인은 그 접속의 SAP 슬롯 상한 안에서 정한다(적재 상세 §2-4). 그래프 적재의 레인은 유형 · 이름 범위로 나눈다(적재 상세 §7-1) |
| slash · `subtype` · 하위유형 · 4-tuple | 객체 유형 표기(예 `TABL/DT` — 구 이름 `adt_slash_type`, 트로브 컬럼 이름 `subtype` · ADT 유형 코드 그대로) · 같은 유형 안의 세부 구분 · 구 시스템의 식별키 네 개 묶음(sid · object_type · slash · name) |
| 원천 값 · 가르는 값 | 하위유형을 가르는 SAP 컬럼 값(예 PROG 의 `TRDIR.SUBC`) · 원천 값 하나가 ADT 코드 둘로 나뉠 때 한 번 더 가르는 다른 컬럼 값(`docs/object_seeker_for_version.md`) |
| 버전 증인(문서 표기 «판 증인」) | 접속이 어느 S/4 버전인지 알려 주는 SAP 구성 요소 · 릴리스(예 S4CORE 109 → 2025)(`release_witness.tsv`) |
| 게이팅(gating) → **패키지 활성화 점검** | 꺼진 패키지의 객체를 **조회에서 «비활성」 으로 표시하는** 검사(숨기지 않는다 · 적재는 막지 않는다 — IG12 · 2026-11-02 사용자 결정). «게이팅」 이라고 쓰지 않는다 |
| (게이팅의) OFF closure → **꺼진 패키지와 그 하위 패키지 전체** | «OFF closure」 라고 쓰지 않는다 |
| 패키지 상태 테이블 | 접속별 패키지 전부와 활성 여부(`package_state`). 원천은 ADT 로 읽고 조회가 조인해 «비활성」 을 표시한다(IG12 · IG17) |
| 필드 목록 · 필드 테이블(`field_set` · `field`) | 테이블 · 뷰 · CDS 필드는 노드가 아니라 필드 테이블의 로우이고, 같은 필드 목록은 모든 접속이 한 벌을 함께 쓴다(적재 상세 §3-6 «저장 1」) |
| 이름 참조 | 필드가 데이터 요소 · 체크 테이블 · 검색 도움말 · 원천 필드를 id 가 아니라 이름 글자로 적은 것 — 읽을 때 그 접속의 노드에서 찾는다(API 설계 §0-1) |
| 적재 유형 · 비적재 유형 | 그래프에 싣는 객체 유형(EQA 45 유형) · 싣지 않는 유형(MSAG · NROB 등)과 적재 유형이어도 싣지 않는 정보(소스 본문 · 메서드 · 테이블 값). 비적재만 라이브로 읽는다(API 설계 §5-1 · MA14) |
| 적재 목록 원천 | 적재가 유형마다 «무엇이 있나」 를 읽는 SAP 테이블 · 이름 컬럼 · 조건(등록부 `ingest_source.tsv` 의 `role=main`) |
| FULL · DELTA | 적재 회차의 종류 — 목록 전체 · 바뀐 것만(후보만)(GR39 · 적재 상세 §7-0-1) |
| 적재 회차 · 미완결 | 적재 묶음을 한 번 도는 것 · 있어야 할 산출이 없어 «정상 종료」 를 선언하지 못한 상태(`incomplete` — 오류 `failed` 와 다르다 · GR53 S1) |
| 시스템 정보(IG19) | 접속 이름 · SID · client · SAP 버전 · ABAP 릴리스. 적재 · 스냅샷 데이터에는 넣지 않고 접속(`conn_id`)만 남긴다 — 복사본이 접속과 어긋나기 때문 |
| 출처 표식 | 적재 상세의 값 출처 표시 — [SQL] SAP 테이블 · [ADT] URI 로만 얻음 · [파싱] 받은 본문 해석 · [계산] 코드가 만듦 · [상수] 고정값 |
| 적재 형식 · 적재 형식 변경 · 변경 번호 | 같은 SAP 입력에 대해 그래프에 쓰는 결과의 모양 · 적재 코드 · 등록부를 고쳐 같은 입력의 결과가 달라지는 것 · 형식이 바뀔 때 유형마다 하나씩 올리는 번호(형식 변경 §1) |
| 유형 해시 · 적재 코드 연쇄 | 옛 판정용 해시(등록부 해시 + 적재 코드 연쇄 해시 — 지금은 기록만) · 적재기에서 import 로 닿는 트로브 모듈 전체 |
| 계획만 · 형식 대조 · 형식 차이 · 맥락 차이 | 계획을 만들되 그래프에 쓰지 않는 실행 · SAP 원천이 그대로인 표본을 «계획만」 해 저장 결과와 비교하는 점검 · 코드 때문에 달라진 점 · 끝점이 생기거나 사라져 맥락 재료(`unresolved_refs` · `targets_no_edge`)만 달라진 점 |
| 특징 · 특징 포함 고르기 · 회귀 목록 · 자동 표본 · 극값 표본 | 저장된 객체 결과에서 뽑는 낱말(예 «`fields` 가 10개 이상」) · 모든 특징이 표본에 2번 이상 들어가게 가장 적은 객체를 고르는 방법 · 결함이 났던 객체처럼 사람이 정해 늘 대조하는 표본 · 회차마다 코드가 고르는 표본 · 가장 큰 쪽이라 꼭 넣는 표본(형식 변경 §15 · `docs/ingest_sample.md`) |
| 계획 기준값 시험 | 작은 가짜 스냅샷으로 유형마다 계획 해시를 내어 기준값 파일과 비교하는 시험(커밋 가드) |
| 보편 참조 객체 · 목록 객체 · 파생 객체 · 멈춘 자리(stub) | 거의 모든 객체가 가리켜 펼치면 응답이 커지는 테이블 · CDS(T001 · MARA …) · 그중 사람이 정한 것 · 그것에 딸려 규칙으로 찾는 것(텍스트 테이블 등) · 연쇄 탐색이 그 객체에 닿아 멈춘 자리(API 설계 §7 «보편 참조」) |
| 주 테이블 | CDS 의 키 필드가 모두 직접 오는 테이블(클라이언트 필드 제외 — 예 I_COMPANYCODE ← T001-BUKRS) |
| 들어오는 연결 수(`in_links`) | 그 노드로 들어오는 엣지 수 — 많이 쓰이는 핵심 객체일수록 크다(검색 순서에 쓴다 · API 설계 §7-30) |

## C. 미러 스냅샷 · 받기

| 용어 | 풀이 |
|---|---|
| 미러 스냅샷 | 같은 PG 안의 **SAP 접속별 스키마**에 정적 · 구조 테이블(DDIC · config · 텍스트 테이블 등)을 복제해 둔 것(사용 중 스냅샷 `mir_<접속 이름>_full`). 적재 · 배치 코드만 읽는다 — MCP tool · 연계 API 는 읽지 않는다(§0-6 · MA21) |
| 받기 | SAP 에서 미러 스냅샷으로 테이블을 복제해 오는 일. 그래프 «적재」 와 다른 일이다 — «받기 완료」 는 적재가 끝났다는 뜻이 아니다 |
| 사용 중 · 작성 중 · 받기 완료 스냅샷 | `_full`(지금 읽는 것) · `_new`(받고 있는 것) · 작성 중 스냅샷의 대상 테이블이 모두 끝난 것(교체하면 사용 중이 된다)(적재 상세 §2-1 · 옛 이름 «세대」 · «닫힌 세대」) |
| `_full` · `_new` · `_dnew` · `_delta` · `_add` | 접속별 미러 스키마 접미사 — 사용 중 · 작성 중 · 작성 중 차이 · 바뀐 것(관측용) · 추가 받기(정의에 새로 더한 테이블만)(CLAUDE.md §1-3) |
| 스냅샷 교체 · 교체 잠금 · 그래프 잠금 | 받기 완료 스냅샷을 한 트랜잭션에서 `_full` 로 바꿔 끼우기 · «사용 중 스냅샷을 읽는 중이니 바꾸지 마」 표시(접속 단위 advisory lock) · 전체 점검(배타)과 적재(공유)를 가르는 잠금 |
| 정의(미러 · 적재) | 받을 테이블 · 필드 · 인덱스와 유형마다 읽을 테이블(적재 조합)을 적은 등록부(`mirror_table` · `mirror_field` · `mirror_index` · `ingest_source`)(적재 상세 §2-9) |
| 읽기 함수 주입 | 적재기는 «SAP 읽기 함수」 를 인자로 받고, 스냅샷을 읽는지 라이브를 읽는지 모른다 — 미러용 사본 코드를 만들지 않는다(IG15) |
| keyset 깊이 · 엿본 로우 · 경계 자르기 | keyset 조건 «앞 d−1 단은 커서와 같고 d 번째 단만 큼」 의 d · 페이지 크기 + 1 번째로 받은 로우(«더 있음」 판정용 · 저장하지 않음) · 꽉 찬 페이지 끝의 같은 키 묶음을 다음 질의로 넘기고 얕은 깊이에서 잇는 것(ADT 설계 §8-4 · §8-7 · IG16) |
| 넓혀 받고 다시 거르기 | SAP 이 리터럴을 바르게 받지 못하는 커서 값(연속 공백 · 큰따옴표)을 LIKE 로 넓혀 보내고 받은 로우를 원래 범위로 거르는 처리(ADT 설계 §8-4) |
| 포기(abandoned) | 추출이 실제로 실패한 테이블의 상태 — «완료」 와 따로 돌려주고 미완결로 끝낸다(IG16) |
| SQL 검증기(`prepare_select` · 문서 표기 «정리기」) | SAP 으로 보낼 SQL 을 검증 · 정리하는 표준 함수(GR23 — 리터럴을 먼저 가린 토큰 열에서만 고친다). 현장 말로 «SQL 정규화기」 에 가깝다 |

## D. MCP API · 응답

| 용어 | 풀이 |
|---|---|
| tool | MCP API 하나(외부 LLM 채팅이 대화 중에 고르는 함수 — `search_objects` · `describe_object` …). 이름에 프로젝트 이름을 붙이지 않는다(API 설계 §0-1) |
| tool 명세(옛 «tool 계약」) | tool 의 이름 · 인자 · 응답. 정본 = 등록부 `mcp.tool` · `mcp.param` · `mcp.text`(정의 등록부 CS6) |
| 응답 공통 구조(문서 표기 «응답 봉투」) | `data` 를 감싼, 모든 tool 이 같은 응답 머리(`ok` · `status` · `found` · `truncated` · `next_cursor` · `coverage` …)(API 설계 §5-4-6). 2026-11-27 결정으로 «공통 구조」 로 쓴다(`it-terms.md` B절) |
| `ok` · `error` | `false` = tool 이 답하지 못했다(인자 · SAP · PG 실패) — «데이터 없음」 으로 읽지 않는다 · 그때의 `{code, message, retryable}`(MA28) |
| `status` — `complete` · `partial` · `pending` · `too_large` | 완결된 답 · 일부만(잘림 · 나눔 · 미완결) · 사람의 선택을 기다림(`choice_required`) · 전송 상한(64 MB)을 넘음. complete 가 아니면 후속 작업을 진행하지 않는다(GR4) |
| `found` — `yes` · `no` · `not_loaded` · `unknown` | 있음 · 없음 · **적재 전(없다는 뜻이 아니다)** · 판정 못 함(읽기 실패)(API 설계 §5-4-2) |
| `in_sap` · `sap_state` | PG 에 없는 주 대상을 SAP 에 존재만 물은 결과 — 있음 · 없음 · `inactive_only`(비활성 버전만 · 개발 중). 없으면 확인하지 않았거나 실패했다(라이브 존재 확인 — `docs/mcp_api_live_presence.md` §7) |
| `reference_only` · `gone` · `loading` · `as_of` | 이름만 있는 노드 · 없어진 객체 · 적재 회차가 도는 중 · 답의 근거가 된 적재 시각(신선도)(API 설계 §5-4-2) |
| `coverage` | 이 답이 어디까지 봤나 — 찾은 원천 · 실린 원천 · 못 찾은 원천과 이유(API 설계 §5-4-6) |
| 크기 세 종류(`size_class`) | `object`(객체 한 건 — 늘 전체) · `list`(목록 — `limit` 100 · 상한 1,000) · `sql`(값 — `max_rows` 100 · 상한 5,000)(API 설계 §5-4-4 · MA16) |
| `size_chars` · `detail` · `filter` · `max_chars` | 나누기 전 전체 크기 · `full` / `summary` · tool 마다 선언한 거르기 조건(모르는 키는 오류 — MA17) · 이 글자 수에서 값 경계로 나눔(API 설계 §5-4-4) |
| 연속 조회(문서 표기 «이어받기」) · `next_cursor` | 나눈 응답의 다음 조각을 받는 것 · 그 위치와 인자 해시를 담은 불투명 글. 서버는 상태를 들고 있지 않다 |
| `X-Max-Result-Chars` | 호출마다 받는 글자 수 상한 헤더(트로브 문서 표기 «머리글」) — 공통 구조 포함 결과 전체가 이 값을 넘지 않게 나눈다(MA31 · MA32) |
| 라이브 | SAP 을 그 자리에서 부르는 것(ADT 주소 또는 freesql). 적재 정보는 PG 만 읽고 라이브로 가지 않는다(MA14) |
| 라이브 존재 확인 | PG 에서 못 찾은 객체 이름을 SAP 의 적재 목록 원천 테이블에 물어 «SAP 에 있음」 만 확인하는 것(`docs/mcp_api_live_presence.md` §7) |
| 주 대상 | tool 이 인자로 받은 객체 하나(또는 `객체-필드`). 결과 목록 안에서 가리키는 객체는 주 대상이 아니다 |
| 논리 명세 · 접속 사전 · `dropped` | SQL 글이 아니라 «주 테이블 · 조인 · 원하는 컬럼」 으로 적은 읽기 정의 · 그 접속의 `DD03L` 을 라이브로 읽은 컬럼 목록 · 그 버전에 없어 뺀 컬럼(MA18) |
| 값 tool · `confirmed` · `choice_required` | 업무 데이터 · 설정 값 · 시스템 상태를 돌려주는 tool(캐시하지 않는다 — GR6) · 같은 묶음에 QAS · PROD 가 있으면 사용자에게 묻도록 `status=pending` + 선택지를 돌려주고, 고른 접속과 `confirmed=true` 로 다시 부른다(API 설계 §5-4-3) |
| 승인(A3) | 값 tool 호출을 사람이 승인해야 하는지 — 읽는 접속의 용도 + 테이블의 전달 클래스로 판정(DEV = 묻지 않음)(MA37) |
| release 계약 C0 ~ C4 | API release 상태의 다섯 계약 — C0 확장점 · C1 시스템 안 사용 · C2 Remote API · C3 Config Contents · C4 Use in AMDP. 응답의 `released` = 사용 계약(C1 · C2)이 RELEASED 계열(MA39) |
| 후보(`candidates`) | 이름 하나가 여러 유형에 있을 때 고르지 않고 돌려주는 객체 목록 — 짐작하지 않는다(API 설계 §5-4-2) |
| 오류 코드 | `invalid` · `invalid_cursor` · `sap_unreachable` · `sap_unavailable`(차단 중) · `sap_auth` · `sap_forbidden` · `sap_error` · `address_unsupported`(읽는 방법이 등록되지 않은 유형) · `busy`(슬롯) · `too_large` · `timeout`(API 설계 §5-4-7) |
| 시간 예산 | tool 한 호출이 쓸 수 있는 시간(240초 · `SiteToolGuard` 가 측정한다 — chat 이 300초까지 기다리므로 먼저 끝낸다)(MA27) |
| 연쇄 탐색 · 노드 단위 · 너비 우선 탐색 | 시작 객체에서 관계를 따라가 닿는 객체 전부를 찾는 것 · 도착한 객체마다 한 번 세는 것 · 가까운 단계부터 넓혀 가는 탐색(BFS)(API 설계 §0-1) |
| 재정렬 창 · 원천별 몫 | reranker 가 다시 점수를 매기는 후보 수(창 밖은 벡터 순서로 남는다) · 문서 원천마다 재정렬 창에 먼저 넣는 상위 건수(API 설계 §7-30) |
| 구조 단위 · 실행 입구 | 구조 tool 이 «안쪽 구조」 를 내는 객체(프로그램 · 함수 그룹 · 클래스 · 서비스 층 …) · 사람이나 다른 시스템이 실행을 시작하는 자리(트랜잭션 · 실행 리포트 · RFC 함수 · 앱 · 서비스)(architecture §8-5-1) |
| 좁히는 조건 · 위아래 커서 | 역설계 대상 목록의 크기를 줄이는 조건 다섯(package · name · origin · changed_since · application) · 다음 · 앞 페이지를 가리키는 `next_cursor` · `prev_cursor`(architecture §8-5) |
| 섹션 · 호출 트리 · 화면 흐름 · 진입 길 | 구조 tool 응답의 묶음 하나 · 이벤트 · 화면에서 PERFORM · MODULE · FORM 을 따라 내려간 트리 · 화면 PBO · PAI · POH · POV 가 부르는 MODULE 목록 · 그 프로그램을 실행하는 트랜잭션과 검사하는 권한 객체(API 설계 §7-26) |
| 직접 호출 목록 | 대상 소스에 적힌 호출을 1단계만 · 빠짐없이 나열한 줄 목록(API 설계 §7-27) |

| 묶음(pipeline) · 묶음 회차(cycle) | 순서가 있는 배치들의 모임(현장 말로 «파이프라인」) · 묶음을 처음부터 끝까지 한 번 도는 것. 트로브 문서의 «묶음」 은 뜻이 여럿이다 — `it-terms.md` G절 |
| 선행 배치 · 시작 배치(root) | 먼저 성공해야 하는 배치 · 선행 배치가 없는 배치(묶음의 일정은 시작 배치만 갖는다) |
| 동시 실행 금지 flag · 프로그램 · 줄(차례) | 켜면 같은 프로그램의 묶음끼리 동시에 돌지 않고 만든 순서대로 하나씩 돈다 · 그 «같은 것」 을 가르는 기준(배치 종류 또는 묶음 템플릿 이름) · 돌 때가 된 회차들의 순서(맨 앞 하나만 돈다) |
| control plane · exec plane | 사람 · 콘솔 · LLM 이 쓰는 필드(켬 · 끔 · 일정 — `desired_state` · `cron_expr`) · worker 만 쓰는 필드(다음 실행 시각 · 커서 · 실패 수)(GR37 · GR38) |
| 전담 표시(lease) | «이 실행을 어느 worker 가 맡았다」 는 표식 — 살아 있다는 뜻이 아니다(GR45) |
| 하트비트(트로브 문서 표기 «생존 신호」) | 살아 있다는 시각 — 프로세스 신호(별도 스레드) · 루프 신호(asyncio 루프가 매 회차) |
| 진척 · 커서(트로브 문서 표기 «진행 위치」) · 체크포인트(트로브 문서 표기 «저장점」) | 처리 건수 · 커서가 실제로 바뀐 것 · 어디까지 처리했나(다시 시작하면 여기서 잇는다 — GR39) · 그것을 중간에 DB 에 확정하는 지점 |
| 보류(hold · `held_at`) | 실패가 이어지거나 멈춤이 의심돼 worker 가 스스로 멈춘 상태 — 사람이 풀어야 다시 돈다(GR41). 사람이 쓰는 «멈춤」(`desired_state=paused`)과 다르다 |
| 쓰는 자원(capabilities) | 배치 종류가 쓰는 외부 자원(`adt` · `models` · `web`). worker 를 가르는 데 쓰지 않는다 — 서킷 브레이커(트로브 문서 표기 «차단기」)와 화면용 |
| 워치독(트로브 문서 표기 «감시」) · 연결 라벨(문서 표기 «연결 이름표」) | 도는 실행이 살아 있는지 · 일하는지 · 막혔는지 보고 조치하는 장치 · DB 연결의 `application_name`(`trove-run-<실행 번호>-<worker>`) |
| mode — full · incremental · typed · home | 회차를 어디서부터 처리할지(진행점)만 정한다. 언제 도는가는 일정이 따로 정한다(GR39) |
| embed-drain | 쌓인 설명 · 문서 청크의 임베딩을 처리하는 시스템 묶음(하나뿐) |
| 임베딩 조절기 · 동시 글 수 · 대량 소비자 | 모델 자원 하나로 들어가는 글 수를 세어 상한을 지키는 공통 코드 · 모델 서버에 보내 놓고 답을 기다리는 글의 합 · 적재 결과를 쌓아 두고 임베딩하는 쪽(적재 상세 §8-0-1) |

## I. 콘솔 대화

| 용어 | 풀이 |
|---|---|
| 콘솔 대화 | 트로브 콘솔 안의 대화 화면 — MCP tool 을 대화로 부른다(산출물은 만들거나 저장하지 않는다)(대화 설계) |
| 자산 · 이름@버전(문서 표기 «이름@판」) | 버전을 붙여 DB 에 저장하는 LLM 입력 재료(System Prompt · Skill 둘뿐 · 이름마다 활성 버전 하나) · 실제로 쓰인 자산을 가리키는 기록 형식(예 `chat_default@3`) |
| 활용 범위(purposes) · 용도별 결속(binding) | 자산이 어디에 쓰이나의 표시(`chat` · `config_interpret`) · 용도마다 기본으로 쓰는 System Prompt · Skill 묶음을 정한 표 |
| 대화 엔진 · run · chat-runner | 사용자 입력 → LLM → tool → LLM … 을 한 번의 응답으로 돌리는 부분 · 사용자 글 하나에 도는 작업 하나 · 그 run 을 돌리는 전용 프로세스 |
| 체크포인트 · 작업 중 입력 | run 이 어디까지 했는지 저장한 자리(끊겨도 여기서 잇는다) · run 이 도는 동안 사용자가 보낸 글(다음 안전지점에 끼워 넣는다) |
| 멈춤 · 카드 | run 이 사람의 결정을 기다리는 상태와 그 결정을 받는 화면 상자 — 승인 · 질문 · 결과 불명 · 선택 카드 |
| 작업 tool · 유형 · 유형별 모두 승인 · 자동 승인 | LLM 이 «하자고 제안」 하는 쓰기 tool(사람이 승인해야 실행) · 승인 묶음 단위(예 `config_gen.summary`) · 카드 안 같은 유형을 한 번에 승인 · 거절하는 버튼 · 대화 하나에서 «묻지 않고 실행」 으로 켜 둔 유형 목록 |
| 결과 불명 | 쓰기 호출이 끊기거나 5xx · 시간 초과로 끝나 «실행됐는지 모르는」 상태 — 사람이 다시 실행 · 건너뜀을 고른다 |
| 버전 고정(문서 표기 «판 고정」 · 코드 `pin_run`) | run 을 시작할 때 쓸 모델 · System Prompt · Skill 의 이름@버전과 생성 파라미터를 값으로 저장하는 것 |
| tool 고르기 | 질문과 비슷한 tool 정의 몇 개만 펼치고 나머지는 요약 목록 + `load_tools` 로 필요할 때 펼치는 방식 |
| HITL | 사람이 중간에 결정하는 흐름(human in the loop) — 카드로 고르고 승인하는 것 |
